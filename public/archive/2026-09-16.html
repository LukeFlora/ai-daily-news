How we contain Claude across products

Anthropic Engineering · 官方技术博客

【推荐理由】该文为企业级 AI 应用提供了极具价值的架构参考，特别是关于如何通过沙箱和流量控制替代低效的人工审批，是构建高权限智能体系统的必读指南。

Anthropic 在本文中探讨了如何通过“限制爆炸半径”（Blast Radius）来安全部署 Claude 智能体。核心观点认为，随着模型能力增强，单纯依赖“人在回路”（Human-in-the-loop）的监督模式因“审批疲劳”（用户通过率高达93%）而失效。因此，Anthropic 转向以“容器化隔离”（Containment）为核心的架构，通过沙箱、虚拟机和出口流量控制等技术手段，从环境层面限制智能体的权限。文章总结了在 claude.ai、Claude Code 和 Claude Cowork 三款产品中的实践经验，强调了在提升智能体自主性与系统安全性之间寻找平衡的重要性。

一年前，我们绝不会允许 Claude 拥有足以破坏内部服务的权限，但现在这已成为常态。风险由“故障概率”和“潜在损害”组成，随着模型能力提升，我们必须通过控制环境来限制“爆炸半径”。我们发现，依赖人工审批的监督模式存在严重的“审批疲劳”问题，用户往往会盲目点击通过。因此，我们重点转向了容器化隔离，通过沙箱和出口控制等手段限制智能体的行为边界。针对不同产品，我们构建了差异化的安全架构，以应对用户误用、模型越狱及环境漏洞等安全挑战。

An update on recent Claude Code quality reports

Anthropic Engineering · 官方技术博客

【推荐理由】该复盘揭示了 AI 产品在“推理延迟”与“输出质量”之间权衡的复杂性，对研发团队在优化 Agent 响应速度时如何避免破坏模型逻辑能力具有极高的参考价值。同时，它强调了在复杂系统变更中，仅依赖自动化评估是不够的，必须建立更精细的用户反馈监控机制。

Anthropic 近期针对 Claude Code 用户反馈的性能下降问题进行了深度复盘。调查发现，问题源于三个独立的技术变更：一是将默认推理强度从“高”降为“中”导致模型智力下降；二是会话缓存清理逻辑的 Bug 导致模型出现“失忆”和重复；三是系统提示词优化过度导致代码质量受损。目前所有问题已在 v2.1.116 版本中修复，Anthropic 承认内部评估未能及时捕捉到这些细微的性能波动，并已重置订阅用户的使用限额以示补偿。

过去一个月，我们调查了用户反馈的 Claude 性能下降问题。经排查，API 层未受影响，问题集中在 Claude Code、SDK 及 Cowork 组件。我们修复了三个关键问题：恢复了被调低的默认推理强度；修复了导致会话频繁重置的缓存 Bug；撤回了导致代码冗余度降低的系统提示词更新。我们承诺将改进评估体系，确保未来能更敏锐地捕捉此类性能波动，并已对受影响用户重置了使用限额。

Scaling Managed Agents: Decoupling the brain from the hands

Anthropic Engineering · 官方技术博客

【推荐理由】该文为构建生产级智能体提供了极佳的架构范式，特别是在处理长生命周期任务时，将执行环境与逻辑控制解耦是避免系统脆弱性的关键。对于需要频繁迭代模型版本或优化复杂 Agent 流程的研发团队，该设计模式具有极高的参考价值。

Anthropic 发布了“托管智能体（Managed Agents）”服务，旨在解决长周期任务中智能体架构耦合度过高的问题。该架构借鉴操作系统设计理念，将智能体拆分为会话（Session）、控制逻辑（Harness）和沙箱（Sandbox）三个解耦组件。通过这种虚拟化抽象，Anthropic 成功避免了“宠物式”容器管理带来的单点故障风险，实现了底层实现与业务逻辑的隔离，使系统能够适应模型能力的快速迭代，并支持未来更复杂的智能体任务。

Anthropic 推出 Managed Agents，通过将智能体的核心组件（会话日志、执行循环、代码沙箱）进行解耦，实现了类似操作系统的抽象层。这种设计不仅解决了模型因上下文限制导致的“焦虑”行为，还通过将“宠物式”的单容器架构转变为可替换的“牛群式”服务，极大提升了长周期智能体任务的鲁棒性与可维护性。

Nikunj Kothari · partner @fpvventures - investing in seed/A. previous: early hire @meter, @opendoor, @atlassian & others. love @shimoleejhaveri + 👦👧

【为何关注】该案例展示了如何通过“去中介化”的闭环支付重构传统行业，对 AI 从业者而言，其核心启示在于：真正的颠覆往往不是优化现有流程，而是通过技术手段彻底移除导致低效的“旧媒介”（如信用卡），从而实现数据闭环与成本结构的根本性优化。

FPV Ventures 合伙人 Nikunj Kothari 领投了燃料支付平台 Piston 的 A 轮融资。Piston 通过绕过传统信用卡网络，利用自有支付轨道解决车队燃油欺诈问题，实现了支付量 8 倍增长及 98% 以上的客户留存率。

我长期以来一直痴迷于“闭环支付”领域，并一直在寻找真正解决痛点的公司……很高兴最终能投资 Piston (piston.com) ⛽️。 仅在美国，每年的燃油支出就高达数千亿美元。大部分支出通过信用卡（信用卡、燃油卡或企业卡）完成。然而，许多卡片甚至没有绑定特定驾驶员，极易被盗、被侧录或滥用。车队所有者不仅要承担欺诈损失，还要耗费大量时间核对账目。加油站既要支付高昂的刷卡手续费，又无法与车队建立直接联系。此前许多公司试图优化现有基础设施，却未能从底层逻辑进行重构。 仅靠制造一张“更好的燃油卡”无法解决问题，因为卡片本身就是症结所在。Piston 决定彻底抛弃卡片，通过自有支付轨道处理交易，无需任何网络或中间商。Piston 直接向加油站付款，再向车队开具发票。每笔交易都绑定了特定的驾驶员、时间、地点和燃油类型，未来还将与车辆本身直接集成。 创始人团队亲历过这些痛点。Vik Sekhon 经营着自己的卡车车队，曾因燃油欺诈遭受真实损失；Shivam 在与 Vik 联手创立 Piston 之前，曾负责管理数千名驾驶员。Piston 对车队最有效的证明是：一旦切换到 Piston，燃油支出会自动下降。我见证了大量图表和客户评价直接印证了这一点。 客户满意度体现在数据上：支付量增长了 8 倍，商户网络增长了 40 倍，留存率保持在 98% 以上。Piston 目前已覆盖全美 48 个州的 2,000 个加油站。车队目前免费使用该服务，并获得了传统卡片系统无法提供的欺诈预防功能；加油站则获得了直接触达车队的机会，有助于建立忠诚度并提供周边产品。 为了扩大覆盖范围，Piston 现已与美国大多数加油站的 POS 系统直接集成。这使他们能够一次性激活数百个加油站，确保供应并满足日益增长的需求。 很高兴能领投他们的 A 轮融资并加入董事会，与现有投资者 Spark Capital 和 Pear VC 并肩作战。特别感谢 Arpan Shah 去年将我引荐给这支团队。
