How we contain Claude across products

Anthropic Engineering · 官方技术博客

【推荐理由】该文为 AI 工程化落地提供了极具参考价值的防御范式：从依赖用户监督转向基于环境隔离的“零信任”架构。对于构建 Agent 产品的团队，文中关于“批准疲劳”的定量分析和多层级容器化隔离策略具有直接的架构指导意义。

Anthropic 在本文中探讨了如何通过“限制爆炸半径”（Blast Radius）来安全部署 Claude 智能体。文章指出，随着模型能力增强，单纯依赖“人在回路”（Human-in-the-loop）的监督模式因用户疲劳（93%的批准率）而存在局限性。Anthropic 转向以“容器化与环境隔离”（Containment）为核心的防御策略，通过沙箱、虚拟机和出口控制等手段限制智能体的操作权限。针对 claude.ai、Claude Code 和 Claude Cowork 三款产品，团队构建了差异化的安全架构，旨在平衡高生产力与系统安全性，并强调了在模型能力提升过程中防御体系同步演进的重要性。

十二个月前，我们绝不会允许 Claude 拥有足以瘫痪内部服务的权限，但现在这已成为常态。风险由“失败概率”和“潜在损害”组成，随着智能体能力提升，我们必须通过限制其环境权限来控制“爆炸半径”。我们发现，依赖用户手动批准的监督方式因“批准疲劳”而失效（用户批准了约 93% 的请求）。因此，我们转而采用容器、虚拟机和出口控制等技术进行环境隔离。本文分享了我们在 claude.ai、Claude Code 和 Claude Cowork 三款产品中，针对不同安全风险所构建的防御架构及实战经验。

An update on recent Claude Code quality reports

Anthropic Engineering · 官方技术博客

【推荐理由】该文展示了在 AI 产品中平衡“推理延迟”与“输出质量”的复杂性，对研发团队如何通过灰度发布和更敏感的回归测试来监控模型性能具有极高的参考价值。

Anthropic 近期针对 Claude Code 用户反馈的性能下降问题进行了深入复盘。调查发现，问题源于三个独立的技术变更：一是将默认推理强度从“高”降为“中”导致的质量下滑；二是会话清理逻辑的 Bug 导致模型出现“健忘”和重复；三是过度压缩冗余的系统提示词影响了代码生成质量。目前所有问题已在 v2.1.116 版本中修复，官方通过重置订阅用户的使用限额来弥补体验损失，并承诺优化内部评估体系以更早识别此类性能波动。

Scaling Managed Agents: Decoupling the brain from the hands

Anthropic Engineering · 官方技术博客

【推荐理由】本文深刻揭示了 AI Agent 架构演进的关键原则：避免将模型能力假设与系统基础设施深度绑定。对于正在开发复杂 Agent 系统的研发团队而言，其提出的“大脑与双手解耦”以及状态与执行环境分离的抽象设计，具有极高的高度指导和实操借鉴价值。

Anthropic 分享了 Claude Platform 中 Managed Agents 的架构设计思考。随着模型迭代（如 Opus 4.5 解决了 Sonnet 4.5 的“上下文焦虑”），Agent 运行框架（Harness）中的假设容易过时。为此，Anthropic 借鉴经典操作系统的虚拟化理念，将 Agent 架构解耦为三大标准组件：Session（只追加日志）、Harness（模型逻辑与路由）和 Sandbox（代码与文件执行环境）。文章探讨了从单容器耦合的“宠物（Pet）”模式向解耦“大脑与双手”架构演进的过程，提升了 long-horizon Agent 任务的稳定性与可扩展性。

Anthropic 工程团队探讨了构建长程运行 Agent 的架构设计。许多 Harness 会对模型的短板做出假设，但随着模型升级（例如为了缓解上下文限制而添加的重置逻辑在更高阶模型上成为了死代码），这些假设很快会失效。为了支持未来未知的程序形态，团队借鉴操作系统的虚拟化抽象（如进程、文件），将 Agent 拆分为 Session（会话日志）、Harness（控制循环与路由）和 Sandbox（代码/文件执行沙盒）三个稳定接口。团队早期曾将所有组件放入单个容器，导致陷入维护“宠物式服务器（Pet）”的困境——容器一旦崩溃或事件流卡顿就会丢失会话。这促使他们必须将“大脑（模型与 Harness）”与“双手（执行环境）”彻底解耦。

我们可能都需要更新对智能体工作负载的认知，结合智能体集群（Agent Swarms）、更强的计算机操作能力、新一代 API 与 MCP 标准，以及 Muse 或 Instinct 等新硬件形态，加上垂直行业智能体、后台工作流智能体等新兴产品，未来将大不相同。 我们将把智能体应用于职业与个人生活中远超预期的任务中。智能体在后台为我们搜集信息并执行工作的体量，将是此前单次 Prompt 交互所能想象的 100 倍。 未来，智能体将 24/7 全天候为你精准招聘人才，从客户业务的每一个信号中捕捉销售时机，处理每一条对话记录以提取产品洞察，审查每一行代码的安全性与 Bug，甚至对系统进行暴力测试，以及处理成百上千种其他任务。 我们目前对智能体的形态、部署方式、管理架构及预算规划的认知，可能仅仅触及了 1% 的表面。但这种规模化的变革已不可阻挡，其程度在过去是难以想象的。 在一个智能体调用系统的频率是人类百倍的世界里，保护企业数据将成为 21 世纪最复杂的安全与治理挑战之一。 重要的是，在 AI 世界中，安全与生产力提升是紧密相连的。如果你给予智能体过多不受限制的信息访问权限，将难以真正管控数据；反之，如果你全面封锁，则无法从 AI 中获得实质性的生产力提升。 我们需要通过现代化的安全与治理手段，以智能化的方式保护企业的系统、环境以及结构化与非结构化数据。 以 Box 为例，我们正在构建保护企业数据及智能体使用权限的新型智能方案。Box Shield 的最新更新提供了基于文档分类级别的细粒度控制，限制智能体可操作的内容。我们还在开发其他功能，以自动检测并预警（或拦截）智能体对数据的异常访问或使用。 这仅仅是个开始。整个行业——从 OpenAI、Anthropic 等实验室，到 Palo Alto Networks、Cisco、CrowdStrike、Okta 等安全平台，以及 Enclave、Method、Alterion、Runlayer 等初创公司——都在进行大量创新，重新思考如何在 AI 智能体时代保护信息。未来充满挑战，也令人振奋。

FPV Ventures 合伙人 Nikunj Kothari 领投了燃料支付平台 Piston 的 A 轮融资。Piston 通过绕过传统银行卡网络、建立闭环支付系统，有效解决了车队燃油欺诈与高额手续费问题，目前已覆盖全美 2000 个站点。

我长期以来一直痴迷于闭环支付，并一直在寻找能够真正解决实际问题的公司……很高兴最终投资了 Piston (piston.com) ⛽️。 仅美国在燃油上的支出就高达数千亿美元。大部分支出通过卡片（信用卡、燃油卡或内部卡）完成。然而，许多卡片甚至没有绑定特定驾驶员，极易被盗、被侧录或滥用。车队所有者不仅要承担欺诈损失，还要耗费大量时间核对账目。加油站既要支付高昂的交换费，又无法与车队建立直接联系。许多公司试图优化现有基础设施，却未从底层逻辑进行重构。 仅靠制造一张更好的燃油卡无法解决问题。卡片本身就是症结所在，因此 Piston 决定彻底抛弃它。它通过自有轨道进行支付，无需任何网络或中介。Piston 直接向加油站付款，随后向车队开具发票。每笔交易都绑定了特定的驾驶员、时间、地点和燃油类型，未来还将与车辆本身集成。 创始人团队亲身经历过这些痛点。Vik Sekhon 经营着自己的卡车车队，曾因燃油欺诈遭受真实损失；Shivam 在与他联手创立 Piston 前，曾负责招聘数千名司机。Piston 对车队的有效性最直接的证明是：一旦切换到 Piston，他们的燃油支出会自动下降。我见过许多直接反映这一点的图表和客户评价。 客户的喜爱体现在数据上：支付额增长了 8 倍，商户网络增长了 40 倍，而留存率始终保持在 98% 以上。Piston 目前已覆盖全美 48 个州的 2000 个加油站。车队目前无需支付任何费用，即可获得卡片系统无法提供的欺诈防护。加油站则获得了与车队直接对接的渠道，有助于建立忠诚度并提供周边产品。 为了扩大覆盖范围，Piston 现已直接与美国大多数加油站的 POS 系统集成。这使他们能够一次性激活数百个加油站，确保供应，从而满足其日益增长的需求。 很高兴能领投他们的 A 轮融资并加入董事会，与现有投资者 Spark Capital 和 Pear VC 并肩作战。特别感谢 Arpan Shah 去年将我引荐给这个团队！ [推文 2] 给 Dreamforce 新访客的公告：在市内通勤时，Lyft 自行车比在 Waymo 或 Uber 里堵上几小时要快得多。SOMA 区的专用自行车道让骑行变得轻而易举。就像开源模型一样，你只用了 10% 的时间就获得了 90% 的价值！
