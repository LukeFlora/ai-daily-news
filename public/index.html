How we contain Claude across products

✦ 洞察

该文为构建企业级 AI 智能体提供了极具价值的工程范式：即通过“环境隔离”而非“人工审批”来控制风险。对于希望在生产环境部署自主 Agent 的团队，文中关于如何通过沙箱和出口控制来最小化“爆炸半径”的思路，具有直接的架构参考意义。

Anthropic 在本文中探讨了如何通过“限制爆炸半径（Blast Radius）”来安全部署 Claude 智能体。核心观点认为，随着模型能力增强，单纯依赖人类监督（Human-in-the-loop）会因“审批疲劳”导致防御失效（用户审批率高达93%）。因此，Anthropic 转向以“容器化（Containment）”为核心的架构，通过沙箱、虚拟机和出口控制等手段，在物理层面限制智能体的操作权限。文章总结了在 claude.ai、Claude Code 和 Claude Cowork 三款产品中积累的工程经验，强调了在提升智能体自主性与保障系统安全性之间寻找平衡的重要性。

📜 原帖中文精译与推文细节
一年前，我们绝不会允许 Claude 拥有可能导致内部服务瘫痪的权限，但现在这已成为常态。部署智能体的风险由“失败概率”和“潜在损害（爆炸半径）”组成。随着模型能力提升，我们无法完全消除风险，因此工程重心从单纯的人类监督转向了环境控制。我们发现，人类在面对频繁的权限审批时会产生疲劳，导致防御失效。因此，我们通过沙箱、虚拟机和出口流量控制等手段，在物理边界上限制智能体的行为，从而在确保安全的前提下，最大化智能体的效能。

该文章展示了在 AI 产品化过程中，性能优化（延迟）与模型推理能力之间的微妙平衡。对于研发团队而言，其“用户反馈与自动化评估不一致”的排查经验，以及对推理强度（Reasoning Effort）的可控配置思路，具有极高的工程参考价值。

Anthropic 近期针对 Claude Code 用户反馈的性能下降问题进行了深度复盘。调查发现，问题源于三个独立变更：一是将默认推理强度从“高”调至“中”以优化延迟，导致模型智能度下降；二是会话清理机制的 Bug 导致模型出现重复性遗忘；三是过度的系统提示词优化反而损害了代码质量。目前所有问题已在 v2.1.116 版本中修复，Anthropic 承诺将改进评估流程，并为受影响用户重置了使用限额。

📜 原帖中文精译与推文细节
过去一个月，我们调查了关于 Claude 响应质量下降的反馈，并定位到 Claude Code、SDK 及 Cowork 中的三个独立问题（API 未受影响）。首先，我们将默认推理强度从“高”调至“中”以解决 UI 卡顿，但该权衡并不理想，现已恢复；其次，会话清理机制的 Bug 导致模型表现出重复性遗忘；最后，旨在减少冗余的系统提示词反而降低了代码质量。所有问题已于 4 月 20 日修复，我们正通过改进评估机制来防止此类问题再次发生。

📜 原帖中文精译与推文细节
